# Backend stabilization audit — Phase 1

Date: 2026-10-15. Baseline: `fix/backend-stabilization` at `86ab48a`, equal to local `main`, local `origin/main`, and the live HTTPS `refs/heads/main` (DbUpdater merge `#72`). The configured SSH fetch failed because this environment has no GitHub SSH key; `git ls-remote` over HTTPS verified the current remote tip. This is a code-path audit, not a live multi-service reproduction. No production code, schema, API contract, commit, or PR was changed.

## Executive summary

The highest-risk path is **reserve → charge → confirm**. Reservation commits a pending order and `Valid` tickets before charging. Failed payment and expiration change only the order status, leaving those tickets in the unique active-seat index. A paid checkout also publishes RabbitMQ messages before its final database save; its domain events publish again from the pre-save interceptor. These are concrete code-path defects with data-integrity and financial consequences. No architectural rewrite is needed to start stabilization, but the payment lifecycle and durable messaging questions belong to issues #53/#54.

Inventory below: **P0 0, P1 8, P2 6, P3 1** confirmed from implementation; 5 additional risks need reproduction. P1 means a core journey can fail or financial/seat state can diverge under a specified trigger. No live PostgreSQL, Redis, RabbitMQ, or loyalty service was available, so severity is provisional where the trigger crosses services.

## Current modules and workflow assessment

The host registers Catalog, Scheduling, Booking, Orders, legacy Application, and one shared EF context. Identity uses ASP.NET Identity and JWT; Catalog imports TMDB data and schedules embedding jobs; Scheduling owns halls, seats, pricing, and sessions; Booking owns Redis temporary locks; Orders creates orders and tickets and coordinates the mock payment and gRPC loyalty service; Tickets owns persisted status; MassTransit publishes purchase messages and consumes loyalty events; Hangfire is registered. Architecture tests cover dependency boundaries, and Orders tests characterize several persistence behaviors. The `CancelExpiredOrdersJob` class exists, but no recurring registration was found in `src/`.

Journey trace: register/login/refresh route through `AuthController` → IdentityService → Identity DB; there is no logout endpoint or refresh-token revocation operation. Browse/session-seat reads combine EF ticket status with Redis locks. Lock → create order validates locks one by one, reserves and commits tickets, then performs GOLD/points/payment and confirms in a separate save. Competing reservations have a PostgreSQL seat row lock and a unique partial ticket index, which protect against two simultaneously valid tickets even if Redis is bypassed. Payment failure, cancellation, and expiry have the defects below. Order history and ticket details check user ownership; admin operations use role attributes. The controller attribute survey found no unguarded order/ticket/user read or admin mutation endpoint; public catalog and scheduling reads appear intentional. Admin rescheduling checks ticket status and overlaps, with a database overlap constraint as a final guard.

### Architectural, performance, and intentional-rule notes

EF warns about required `Order → Session` and legacy `SeatLock → Seat` relationships with filtered principals. The former can make `Include` queries drop orders; the latter maps an unused legacy entity. Query-specific fixes should precede schema changes. The active-ticket unique partial index plus PostgreSQL seat row locks are intentional safeguards; retaining them is important. Ten-minute lock/order lifetime, ten-minute cancellation cutoff, maximum 10 seats, mock payment, and GOLD's one-ticket discount appear to be current business rules. Some reads have extra round trips, but no measured performance defect justifies optimizing them in this phase. TMDB import checks duplicates before its transaction and relies on the unique external-ID index; concurrency behavior should be tested before changing the flow. Catalog enqueues embeddings after commit, so enqueue failure can leave a movie without an embedding job; this is a lower-priority operational risk.
