# Checkout and payment decoupling — final integration review

## Current sequence and Phase 1 API

Before this phase, `POST /api/orders` validated seat locks, called `OrderReservationService`, committed a `Pending` order and `Reserved` tickets in PostgreSQL, then called `OrderCheckoutOrchestrator`. It returned the checkout result, so a decline could still leave a persisted order. The orchestrator claims `Pending -> PaymentProcessing` with a conditional PostgreSQL update before calling loyalty or `IPaymentService`. Confirmation persists `Paid` and `Valid` together; a definitive decline persists `Failed` and `Released`; an ambiguous result retains `Reserved` and becomes `PaymentOutcomeUnknown`. No transaction spans the provider call. The ticket partial unique index and the claim also protect expiration and pending cancellation races.

Phase 1 adds `POST /api/orders/reservations` with `{ sessionId, seatIds }`. It uses the same lock validation and reservation service and returns `{ id, totalAmount, status: "Pending" }`. It does not call payment, GOLD, or loyalty. `POST /api/orders/{id}/checkout` accepts `{ paymentToken, useLoyaltyPoints, applyGoldUpgrade }` and returns the existing order ID result. `GET /api/orders/{id}/status` returns `{ id, status }` for its owner. Checkout loads the persisted order and tickets, checks ownership and lifecycle eligibility, and uses the existing atomic claim and outcome handling. The old `POST /api/orders` body and reserve-then-checkout behavior remain available and share these services. `GET /api/orders` still returns order history.

Clients may move to: lock seats, create a reservation, store its ID, start checkout once, then read status after a timeout. A paid retry returns the order ID. Processing, unknown, failed, expired, and cancelled orders reject another charge; an uncertain result requires reconciliation, not a new checkout request. The new reservation route does not provide request idempotency: retrying creation after a lost response may create a second order or hit seat uniqueness. Coordinate frontend migration before changing the old POST; no frontend code was changed. The mock payment provider and current response conventions are retained.

## Ownership and provider boundary

Orders owns creation, seat reservation, ticket price snapshots, totals, `Pending`/`PaymentProcessing`/`Paid` lifecycle, confirmation, expiration, and cancellation decisions. Checkout applies the existing GOLD and loyalty rules while Orders remains the coordinator. Future Payments owns durable payment and refund attempt IDs, provider idempotency keys, provider calls and webhooks, result lookup, and reconciliation. Provider SDK types and credentials must stay outside Orders.Domain; opaque confirmed provider references are retained as source facts. `Order.PaymentTransactionId` currently records the successful provider transaction for confirmation and refund; it cannot identify an in-flight attempt.

`IPaymentService.ProcessPaymentAsync(amount, currency, paymentToken, ct)` and `PaymentResult` are the existing provider-neutral boundary. `PaymentResult` carries success with a transaction ID, a definitive failure code, or the current `payment_outcome_unknown` code. The contract is sufficient to keep payment execution out of order creation, but insufficient for production recovery. A future Payments contract must accept a durable attempt identity and provider idempotency key, return a provider-neutral attempt/outcome identity, and support querying a definitive outcome by that identity. Persist the attempt under Payments ownership before dispatch; correlate it with order ID and checkout request ID. A refund needs its own attempt identity and lookup. Order status alone is neither provider idempotency nor proof of payment. No PaymentAttempt entity is added to Orders.Domain or to the database in Phase 1.

The current PostgreSQL claim guarantees at most one concurrent caller of a Pending order starts a charge in this application path. It does not distinguish a crash just before the provider call from one after the provider received it. The mock provider does not offer authoritative lookup or idempotency. Do not automatically retry `PaymentProcessing` or `PaymentOutcomeUnknown`. Reconciliation must ask the real provider through Payments and then apply a definitive paid or failed transition with the existing tickets. A successful charge followed by failed local confirmation likewise requires reconciliation. Duplicate reservation requests remain a separate API idempotency problem.

## GOLD, loyalty, and refunds

Reservation-only creation saves base ticket prices and has no loyalty side effects. At checkout, GOLD eligibility and discount are calculated from the persisted session and reserved ticket snapshots. `UseGoldUpgradeAsync` consumes the upgrade before payment; the order discount and upgraded ticket are saved before points deduction. A retry after precharge reset sees `IsGoldUpgraded` and does not consume a second upgrade. Loyalty points are calculated and deducted before payment using the deterministic order refund/deduction keys; `PointsUsed` is recorded when purchase is confirmed. A definitive payment decline attempts point refund and GOLD rollback. An uncertain result retains the reservation and upgrade for reconciliation. A confirmation failure can leave external GOLD/points effects and a discounted order without a confirmed purchase. The persisted ticket upgrade and price snapshot, order total, points, and successful transaction ID are the available reconciliation evidence; an attempt record is still needed. No second deduction path was introduced.

Paid cancellation now persists one durable lifecycle owner before payment, points and GOLD compensation. The source snapshot retains the original nullable currency and cash facts; zero cash never calls the payment provider. Money intent commits before the legacy call, and referenced success commits before later compensation or Order/Ticket finalization. Uncertain outcomes cannot be redispatched because the legacy interface has neither an idempotency key nor lookup. Only the verified idempotent Loyalty operations resume automatically through a caller retry. Finalization reloads and verifies the claimed source, then commits `Cancelled`/`Refunded` together. See the durable cancellation protocol below; Pending cancellation is unchanged.

## Phase 2 transactional messaging

The existing `ApplicationDbContext` maps MassTransit's `inbox_state`, `outbox_state`, and `outbox_message` tables. `AddEntityFrameworkOutbox<ApplicationDbContext>` uses PostgreSQL and the Bus Outbox. Its background delivery service sends committed rows to RabbitMQ and removes delivered messages.

Three purchase messages retain their separate contracts. `TicketPurchasedEvent` is the existing general purchase notification; `TicketPurchasedMessage` drives the local ticket PDF email consumer; and `NestJsTicketPurchasedEvent` addresses the loyalty queue. Only the local ticket email message requires a recipient email; Loyalty staging is email-independent. All critical checkout publishers inject scoped `IPublishEndpoint` or `ISendEndpointProvider`, which the Bus Outbox replaces; none injects `IBus`.

Checkout tracks Paid and Valid first, stages `TicketPurchasedEvent`, then calls the final `SaveChangesAsync`. During that save, `DispatchDomainEventsInterceptor` publishes `OrderPaidEvent` in process. Its handler stages the ticket email and loyalty messages using the tracked final paid state. EF persists the order, tickets, and outbox rows in one PostgreSQL transaction. The direct purchase event is staged in one place and is not also sent by the domain handler. A rolled-back Order transaction leaves no deliverable message. A committed transaction keeps its messages while RabbitMQ is unavailable; the outbox worker retries delivery later.

The interceptor dispatches wrapped Redis and SignalR notifications only after a successful implicit EF save. Pending cancellation uses an explicit transaction and dispatches the buffered notification after `CommitAsync`. A failed save does not run those callbacks. Failed Redis or SignalR callbacks are logged and do not reverse a committed Order. These callbacks are best effort, not durable: a crash after commit can lose them. PostgreSQL status remains authoritative for clients. Existing SignalR method names and payloads, Redis keys, and owner-only unlock scripts are unchanged.

Reservation-only creation has no payment, loyalty, or purchase message. The processing claim and an unknown payment outcome also emit no purchase message; an unknown outcome keeps Reserved tickets. A definitive decline saves Failed/Released before best-effort Redis unlock. Pending and paid cancellation save their respective ticket state before best-effort Redis unlock and SignalR seat notifications. Expiration already commits before its best-effort notifications. Reservation-failure and pre-charge lock cleanup remain separate from post-commit Order notifications.

The local `TicketPurchasedConsumer` uses the EF Consumer Outbox/inbox to suppress repeat processing of a completed MassTransit message ID. Its PDF email is external: a crash after sending email but before the inbox commit can still send it twice. The two local loyalty email consumers accept raw external messages without a verified stable message ID, so consumer persistence was not enabled for them. The NestJS loyalty consumer is outside this repository and must deduplicate by order/event ID. Delivery is at least once; no end-to-end exactly-once guarantee is claimed.

The Bus Outbox also affects the scoped profile publishers. `UpdateProfileCommandHandler` and `SetMyDateOfBirthCommandHandler` stage their existing messages before `UserManager.UpdateAsync` performs the identity save. Sending afterward would leave messages only in the EF change tracker. If staging throws, the handler now returns `User.MessageStagingFailed` without saving the identity change. Successful responses retain their existing shapes.

Once messages are staged successfully, the identity row and outbox rows share the same EF save and rollback together. The local ticket email endpoint retries PostgreSQL serialization conflicts three times, one second apart, so concurrent delivery of the same MessageId can resolve against the committed inbox row. Other failures follow the broker's error handling and may need an operational replay; SMTP is not exactly once. Replaying the same uncompleted `MessageId` may run the consumer again, while a completed inbox entry suppresses it. A different `MessageId` for the same Order is a distinct message and requires business-level duplicate handling if that behavior is needed.

MassTransit runtime packages were aligned to 8.5.5 with `MassTransit.EntityFrameworkCore` 8.5.5. The originally pinned 8.5.8 runtime was binary incompatible with the EF 9 compatible 8.5.5 delivery worker (`AsyncEnumerableExtensions` type load failure). The 8.5.8 outbox package selects EF Core 10 on this application's .NET 10 target, so aligning on 8.5.5 avoids an EF Core major-version change. The PostgreSQL/RabbitMQ delivery test exposed the incompatibility and verified the correction.

Migration `AddMassTransitOutbox` is in the existing Infrastructure history and only adds the three MassTransit tables and indexes. Apply it with Cinema.DbUpdater before starting application instances that use the Bus Outbox. Rollback refuses to drop the tables while `outbox_message` contains undelivered rows; operators must drain or explicitly handle those messages first. Existing Order/Ticket tables and lifecycle indexes are unchanged.

PostgreSQL integration tests verify rollback leaves neither a Paid order nor an outbox row, commit retains Paid/Valid with the row, and the production domain handler stages each of the three purchase contracts once. A recovery test commits while the configured RabbitMQ endpoint is unreachable, confirms the row remains, then starts the delivery service against real RabbitMQ and verifies the delivered event payload. A consumer test verifies that a repeated MessageId sends one email and a distinct MessageId is processed separately. The DbUpdater test applies the migration to existing Order/Ticket records and checks all three outbox tables. Existing Redis ownership tests still run against real Redis. These checks do not cover a process crash between an external email and its inbox commit or an actual payment provider outage.

## API compatibility and frontend migration

The Orders controller requires authentication for all four checkout routes. Reservation creation and legacy creation use the caller's user ID. Separate checkout and status lookup filter the persisted order by that user ID; an unknown or foreign ID returns `Order.NotFound` (HTTP 404). An ineligible checkout returns `Order.InvalidState` (HTTP 400), except a paid retry returns the original ID. The new literal `reservations` route and GUID-constrained `/{id}/checkout` and `/{id}/status` routes do not overlap `POST /api/orders` or `GET /api/orders`. The existing POST body, `Guid` success response, and error envelope remain unchanged. A manual Production-mode HTTP smoke test after migration confirmed the routes in Swagger and HTTP 401 for unauthenticated requests to the legacy create, reservation, checkout, and status routes. Ownership and response conclusions come from controller inspection and handler tests; this repository has no automated ASP.NET Core test host for authenticated end-to-end coverage.

Frontend migration: (1) lock seats and `POST /api/orders/reservations`; (2) show its `Pending` status and base `totalAmount`; (3) submit the stored ID to `POST /api/orders/{id}/checkout`; (4) read `GET /api/orders/{id}/status` after the checkout response or a timeout; (5) treat `PaymentProcessing` and `PaymentOutcomeUnknown` as non-final and await reconciliation. A paid retry is safe; do not retry an uncertain charge. The reservation total is a base quote. A requested GOLD upgrade and loyalty points are evaluated at checkout against the persisted tickets and current eligibility; the final payable amount can differ. The API does not guarantee that the reservation quote is a locked final price. A future client should request a checkout preview and explicitly accept any changed amount before submitting a charge.

## Deployment and rollback

Apply migrations with `Cinema.DbUpdater` before starting any application instance that uses the Bus Outbox, then confirm the delivery worker and RabbitMQ connection. Production startup does not migrate the database; Development startup invokes the existing initializer. Running the new worker against the previous schema would fail because the three MassTransit tables do not exist. `AddMassTransitOutbox` only adds those tables and their keys and indexes; the previous Order, Ticket, and partial seat uniqueness indexes remain. Its rollback guard rejects dropping an outbox that still has undelivered messages. Drain or explicitly transfer those messages before rolling back, and never delete them merely to complete rollback. An older application version cannot deliver pending outbox rows. Rolling back also removes inbox deduplication history, so a later broker replay may repeat local email delivery.

## Remaining consistency risks and Payments handoff

The outbox closes the PostgreSQL-versus-RabbitMQ gap for staged purchase messages. It does not make payment, GOLD consumption, points deduction/refund, Redis, SignalR, or email atomic with PostgreSQL. A payment can succeed while final confirmation fails and then needs reconciliation. GOLD and points are still used before payment, with compensation on definitive failure only. Unknown payment outcomes are not treated as declines. Paid cancellation persists its durable owner and dispatch intent before calling the refund provider, then records referenced success before saving Cancelled. Unknown legacy refund outcomes require authoritative reconciliation and are never automatically redispatched. RabbitMQ delivery failure alone no longer causes a payment refund.

Future Cinema.Payments owns persisted charge and refund attempts, provider idempotency keys, authoritative outcome lookup, webhooks, and reconciliation for processing or unknown payments and interrupted refunds. Its contracts with Orders must identify the order, attempt, provider-neutral outcome, and definitive transition. It must reconcile legacy `Pending`/`Valid` records and charge-success/confirmation-failure cases without blindly retrying a provider call. External loyalty consumers must deduplicate purchase messages by stable order or event identity; the local Consumer Outbox deduplicates a completed MassTransit `MessageId`, not distinct messages with the same business order. SMTP, Redis, SignalR, provider calls, and loyalty calls remain outside the database transaction. In particular, a crash after sending email but before the inbox commit may repeat email, and a crash after the Order commit but before a post-commit callback may omit a live notification. PostgreSQL status is authoritative.


## Durable refund foundation (inactive)

RefundOperation, RefundProviderObservation, IRefundProvider, RefundOperationStore, OrdinaryRefundAdmission and RefundExecutor are NOT registered with DI, any endpoint, Hangfire or a hosted worker. The active CancelOrder handler delegates paid cancellation to the separate durable owner protocol below. Pending cancellation, charge API, points RPC, GOLD, session completion and event contracts retain their existing policy. Checkout confirmation additionally retains the currency of its actual payment instruction. There is no confirmed-refund event yet.

PersistApprovedAsync persists an already-authorized instruction; it does not make an H-16 admission decision. It checks Paid order identity, charge reference, full positive PaidAmount, persisted PaidCurrency, UserId, SessionId and PaidAt under a short Order UPDATE lock with a 3-second lock timeout. No Session/Hall/Ticket eligibility is evaluated by this low-level method. Its equivalent replay comparison includes the original ApprovedAtUtc and admission JSON. OrdinaryRefundAdmission supplies the separate verified admission boundary below. Zero cash is rejected before a provider operation can be created.

Order.PaidCurrency is a nullable confirmed payment fact. Checkout passes one currency instruction to both the existing provider call and the Paid transition; the current charge currency remains UAH. Refund currency comes from the committed order, never current configuration or client input. Confirmed currency cannot change through replay, EF writes or ordinary SQL updates. NULL means unverified historical currency or no monetary amount, not UAH. The additive AddAuthoritativePaidCurrency migration performs no backfill. Legacy instructions with missing/mismatched currency are stopped before new provider dispatch with ReconciliationRequired / ORIGINAL_CURRENCY_UNVERIFIED; existing provider observations remain retained. Verified historical correction requires a future explicitly controlled process. Exact Kyiv seven-day/DST semantics, unknown EndTime and Used-ticket policies remain prerequisites for live activation.

One logical full refund per order is enforced by PostgreSQL uniqueness; operation ID and its derived provider key are immutable. Equivalent retries with another proposed ID return the original operation; conflicting immutable content is rejected. The original approval time does not move. EF guards and PostgreSQL triggers protect approval identity and append-only provider observations.

States are Approved -> Dispatching -> Succeeded / Declined / Pending / Unknown / ReconciliationRequired. Each claim has a new token and PostgreSQL-time 30-second lease. The automatic budget is eight claims including crashes, with exponential backoff from 10 to 300 seconds after unresolved results. Expiry means possibly dispatched, never failed. The final interrupted attempt becomes ReconciliationRequired. A known successful observation can resolve an expired operation even after budget exhaustion without another money call; an active newer lease is not overwritten.

Each DB phase uses a fresh context and zero-retry execution scope; global Npgsql retries stay enabled. No provider call runs under a PostgreSQL lock or transaction. After a lost commit acknowledgement, query the stable identity from a fresh scope; never replay the callback blindly.

Recovery uses authoritative provider lookup where supported. Pending/Unknown remain uncertain. Redispatch requires stable provider idempotency with the original key and identical payload. Even NotFound does not permit reissue without that guarantee, because the original call could still be in flight. Without safe capabilities the operation requires reconciliation. Adapter idempotency guarantees must cover the whole recovery period; expired keys cannot be advertised as safe.

The provider token requests a 10-second deadline, not a hard cancellation guarantee. Adapters must bound their own I/O. The executor awaits the actual task to retain late returned success. Returned evidence uses a separate bounded 10-second persistence token even if the caller disconnected. Database outage can still prevent recording: authoritative provider lookup/idempotency or manual reconciliation remains necessary.

Observations commit independently before fenced head resolution. A stale worker can append monetary evidence but cannot change a newer claim. No Order/Ticket projection is attempted, so its failure cannot roll back retained success. Definitive success requires a provider reference. Conflicting observations for one claim are rejected. Future confirmed-refund projection/source/outbox code must preserve this evidence-first boundary.

Provider observation timestamps are normalized to PostgreSQL microseconds before persistence and replay comparison. Submicrosecond ticks do not create false replay conflicts; differences at persisted precision remain conflicts. Observation and resolution serialize on the operation row. If success and decline observations contradict each other, both immutable observations remain and the operation becomes ReconciliationRequired with CONFLICTING_PROVIDER_OUTCOMES regardless of outcome or commit order. Recovery also checks both outcomes before promoting an expired unresolved operation. This contradiction cannot automatically promote to Succeeded or dispatch another money call; a controlled authoritative reconciliation decision is required.

Provider references are retained in full as PostgreSQL text, including late successful responses. The additive PreserveFullRefundProviderReferences migration widens only that observation column; it does not rewrite evidence or weaken immutable guards. Downgrading to the old 256-character limit is not a lossless rollback for longer retained references and must not truncate monetary evidence.

The only new provider implementation is a TEST-ONLY PostgreSQL fixture with independently durable outcomes, strict key/payload ownership and stable lookup/reference. A separate console process exits after provider commit before returning a response; another process reads the outcome. This proves deterministic mock restart behavior, not real payment-provider guarantees. Existing MockPaymentService is unchanged.

The additive migration creates two tables, constraints, indexes and immutable-write triggers only. It does not alter old orders or create approvals. Down removes monetary evidence and is not a routine lossless rollback; evidence preservation and explicit approval are required before using it on retained operations.

Before activating RefundOperation execution: settle exceptional/admin admission policies, reconcile historical currency where needed, select and test a real adapter, wire durable approval and recovery together, then add its Order/Ticket confirmation, points/GOLD compensation, confirmed-refund source/Outbox and passive Loyalty as separate slices. The active paid cancellation journal is mutually exclusive with this foundation and does not activate it.

### Internal ordinary admission (inactive)

ApproveAsync accepts only order ID and a request correlation ID. Actor/owner come from ICurrentUserService; there is no admin bypass or public endpoint. The request identity is scoped to the customer's order. Different request IDs for an equivalent ordinary request return the original operation, approval time, provider key and admission evidence. An unrelated principal cannot retrieve it, and another approval policy cannot be relabelled as ordinary.

One READ COMMITTED transaction takes Session SHARE -> Order UPDATE -> ordered Tickets UPDATE, with a 3-second lock timeout and no automatic transaction callback replay. Session SHARE conflicts with the existing Hall -> Session lifecycle UPDATE; admission never takes Hall or Seat locks. Fresh source reads verify Paid status, original cash amount/currency/charge/time, matching Valid tickets and totals, and completed/consistent GOLD ownership without recovery flags. PostgreSQL clock_timestamp() after row locks supplies ApprovedAtUtc. Ordinary approval requires StartTime - ApprovedAtUtc > 60 minutes; exactly 60 is rejected. EndTime/OccupancyEndTime are not substituted or needed for this ordinary rule.

The immutable snapshot records the original session start/status, payment and loyalty totals, GOLD flags/ownership, all qualifying ticket facts, policy version and original request ID. Operation insertion commits before any later network work. A lock timeout returns Refund.Busy for a safe same-identity retry; a lost commit response requires a fresh authenticated lookup/replay, never a blindly repeated callback. Replays do not re-evaluate or extend the original deadline.

Admission retains historical evidence; its durable RefundOperation now fences application ticket validation. Validation uses Session SHARE -> Order UPDATE -> Ticket UPDATE, reloads tracked state, checks the Paid order and durable refund ownership, and commits Used atomically. Two concurrent validations cannot both succeed. All RefundOperation states block use, including Declined: there is no approved access-reopening resolution, and late contradictory provider evidence is possible. Lease expiry, timeout or budget exhaustion does not reopen access. The existing Admin authorization and UTC same-day rule remain; the optional built-in TimeProvider only makes date-sensitive tests deterministic. No new TicketStatus or migration is introduced.

### Active durable paid cancellation

`IPaidOrderCancellation` coordinates the existing endpoint through a unique retained `PaidCancellation` per paid Order. Its immutable snapshot contains caller/owner/session, charge, cash amount, nullable original currency/time, points, GOLD ownership and exact ticket facts. There is no historical backfill. Session SHARE -> Order UPDATE -> ordered Tickets UPDATE protects eligibility and owner insertion atomically. The live ten-minute customer cutoff and Admin bypass are unchanged; the inactive ordinary policy's sixty-minute rule is not substituted. Both owner tables also touch the unchanged Order identity in their insert triggers, preventing direct inserts from authorizing a second operation. The MVCC write forces a competing older repeatable-read snapshot to abort with a serialization conflict instead of missing the committed owner.

Execution uses fresh DI scopes with the existing scoped context/interceptor/outbox graph. A two-minute execution lease selects one worker; each external step's intent is committed first. Lease expiry cannot prove that money did not move: abandoned Dispatching becomes Unknown, never Ready. Generic `PaymentResult.Failure` supplies no authoritative refund-decline evidence and also becomes Unknown. Referenced success is retained in its own transaction before points, GOLD or finalization. A lost commit acknowledgement is queried through the persisted identity from a fresh scope, without callback replay or another provider call. Request disconnection does not cancel outcome persistence. Network tokens request ten-second timeouts; adapters must bound their I/O and the coordinator awaits actual returned evidence.

Only verified Loyalty compensation may replay: points retains `DeterministicGuid.Create($"refund-{orderId}")`, with Loyalty's exact command key/payload/result record and debit linkage; GOLD rollback uses its user/order reservation and released-at no-op. These semantics were checked read-only against Loyalty `origin/master` commit `87b9caac7ba452eab0586ceee779b45cef491239`. Completed step evidence survives later failure. A positive-cash order with NULL PaidCurrency is rejected inside Claim before inserting any journal (Order.CurrencyReconciliationRequired), leaving Paid/Valid and normal ticket use unchanged. Existing journal recovery is not rewritten. Zero cash uses the same journal for points/GOLD without any RefundOperation or provider call.

Finalization obtains fresh lifecycle locks, reloads Order/Tickets, verifies the original snapshot and every successful compensation, and atomically saves Cancelled/Refunded plus the finalized journal. Used can never be overwritten through stale tracked tickets. Existing Redis/SignalR notifications dispatch only after transaction disposal. A projection failure leaves success evidence available for a fresh caller retry. A finalized owner returns retained success after a lost response; unrelated callers still receive Order.NotFound, and cancelled historical orders without an owner retain Order.AlreadyCancelled. Uncertain money requires controlled reconciliation; no new endpoint, automatic recurring worker, provider lookup or provider exactly-once guarantee is introduced.

The additive AddDurablePaidCancellation migration adds only the journal, uniqueness/checks, cross-owner arbitration and immutable evidence triggers. It does not modify historical orders or fabricate payment facts. Down removes retained recovery evidence and owner guards; it is only a disposable-test rollback without a separate reviewed production evidence-preservation plan.

Deployment requires coordinated writer replacement, not a rolling mix with old replicas. First stop admitting cancellation, ordinary approval and ticket-validation work on old application replicas, and drain all in-flight operations, especially legacy provider calls. Establish the outcome of interrupted legacy calls before allowing a new owner for those orders. With old writers stopped, apply the additive schema migration, then start only code versions that enforce the new ownership protocol on every cancellation, approval and validation path. An old replica that already passed preflight can otherwise refund or consume a ticket without observing the new claim; the database journal does not retroactively fence that external call. Do not roll back to unfenced binaries while retained claims or in-flight recovery exist. If rollback is necessary, stop writers and preserve the journal/schema while preparing a reviewed fenced rollback or reconciliation plan; do not drop evidence or reset uncertain steps to Ready. This PR does not execute any deployment or shared migration.

Admission lock timeouts return Ticket.Busy / Order.Busy without mutation or network effects. Validation uses a zero-retry scope and rejects an outer automatically retrying scope; ambiguous commit errors are not treated as rollback. Fresh validation after a committed-but-unacknowledged use returns Ticket.Used. Zero-cash orders produce no monetary RefundOperation; the active cancellation journal handles their verified points/GOLD compensation. Exceptional admin admission and Used-ticket refund policies for the inactive foundation remain separate stages.

The currency migration adds one nullable column, a format/source CHECK and an immutable-currency trigger. Existing paid rows retain their exact old facts with NULL currency. Down drops retained currency evidence and is not a routine lossless rollback; preserve evidence and obtain explicit approval before applying it outside disposable tests.


## Final Orders / Payments / Loyalty integration handoff

Scope: integration preparation only. This section states requirements for a future in-process Payments module; it does not add that module, provider adapters, callbacks, APIs, database changes or activation. The existing interfaces remain the implementation starting point. Source baseline: backend merge of #98 (`e2f2a030cfcda78963b518d19673e9827bb37d7e`); Loyalty inspected read-only at `87b9caac7ba452eab0586ceee779b45cef491239`.

### Ownership and existing consumers

| Owner | Responsibility | Existing boundary / limitation |
| --- | --- | --- |
| Orders | Reservation/checkout rules, prices, Order/Ticket lifecycle, refund eligibility, durable cancellation ownership, lifecycle fencing, final business transitions and business Outbox facts | OrderCheckoutOrchestrator, OrdinaryRefundAdmission (inactive), PaidOrderCancellation (active legacy path), scoped EF Bus Outbox. Payments must not mark tickets Used/Refunded or decide eligibility. |
| Future Payments | Durable charge/refund attempts, provider adapters/references/idempotency, authenticated callbacks, authoritative lookup, uncertain-outcome reconciliation and provider error classification | Implement the existing provider boundary where sufficient; no separately deployed service is required. Do not take ownership of Orders admission, Loyalty accounting or a second independent refund for the same Order. |
| Loyalty | Debit-linked restoration of spent points, GOLD reservation ownership/rollback, purchase rewards/reversals and later debt; persistent business-command/event idempotency | Existing ILoyaltyService/proto and consumers remain unchanged. A payment provider's idempotency is not Loyalty deduplication. |

Current signatures (see [IPaymentService](../src/Cinema.Application/Common/Interfaces/IPaymentService.cs) and [IRefundProvider](../src/Cinema.Application/Common/Interfaces/IRefundProvider.cs)):

```csharp
Task<PaymentResult> ProcessPaymentAsync(decimal amount, string currency, string paymentToken, CancellationToken ct = default);
Task<PaymentResult> RefundPaymentAsync(string transactionId, CancellationToken ct = default);
Task<RefundProviderOutcome> SubmitAsync(RefundProviderRequest request, CancellationToken ct);
Task<RefundLookup> LookupAsync(RefundProviderRequest request, CancellationToken ct);
```

`PaymentResult` has IsSuccess, TransactionId, ErrorMessage and FailureCode. Checkout recognizes `payment_outcome_unknown`; this legacy result is not a durable attempt record or a general four-state outcome protocol. The legacy refund method accepts only the original charge reference: it supplies neither a stable refund idempotency key nor lookup, amount/currency verification or provider occurrence time. Its generic Failure cannot prove definitive refund decline. MockPaymentService remains the active mock; do not infer real-provider guarantees from it.

The stronger **inactive** refund boundary already defines:

- `RefundProviderRequest(OperationId, IdempotencyKey, ChargeReference, Amount, Currency)`.
- `RefundProviderOutcome(Kind, ProviderReference?, EvidenceCode?, ProviderOccurredAtUtc?)`, with Succeeded / Declined / Pending / Unknown.
- `RefundLookup(AuthoritativeNotFound, Outcome?)`; SupportsStableIdempotency and SupportsAuthoritativeLookup must describe verified adapter guarantees, including retention windows and conflicting-payload rejection. AuthoritativeNotFound alone does not authorize redispatch of a possibly in-flight request.

Use IRefundProvider for future refund integration; do not add a parallel refund-provider abstraction. RefundExecutor, RefundOperationStore and OrdinaryRefundAdmission remain unwired to public APIs/workers. Moving the active legacy cancellation journal to this foundation needs an explicit ownership handover: never create a second monetary owner or provider key for the same Order. A proposed charge attempt/lookup extension of IPaymentService must be separately reviewed; no such API exists today.

### Identity, value and time contract

| Term | Ownership and required meaning |
| --- | --- |
| OrderId | Orders' stable business UUID, shared by purchases/refunds/Loyalty. Not a provider charge or PaymentAttemptId. |
| PaymentAttemptId | Future Payments' persisted internal attempt identity, allocated before dispatch and correlated durably with OrderId and checkout intent. Not implemented today; PaymentProcessing is not an attempt ID. Duplicate equivalent intent resolves the same attempt; a genuine subsequent charge requires an explicitly permitted new business attempt. |
| RefundOperationId | Existing RefundOperation.Id is an immutable approved full-cash instruction; RefundProviderRequest.OperationId carries it. PaidCancellation.Id is a separate current lifecycle journal ID, not automatically a new RefundOperationId or provider reference. Preserve whichever owner already exists during integration. Payments may own execution-attempt/observation IDs mapped to this sole business operation; these never authorize a second refund. |
| ChargeReference | Opaque original provider charge identity; currently Order.PaymentTransactionId for positive-cash payments. It identifies the charge to refund, not a refund attempt. A zero-cash compatibility transaction marker is not evidence of an external charge. |
| ProviderReference | Opaque provider-specific charge/refund result reference; distinguish operation type/provider account context. Retain full values and their association with the original attempt. It is not an internal operation ID. |
| IdempotencyKey | Payments owns provider keys tied to immutable attempt/payload; current RefundOperation.ProviderKey is `refund:` + operation UUID in N format. Required future charge data: stable PaymentAttemptId + OrderId/checkout-intent correlation, immutable amount/currency/provider-account context, durable dispatch state, provider charge reference, classified outcome, verified provider time when available, local observation time and retained evidence. Persist the attempt before external execution. A success must be correlated and source-checked before Orders confirms Paid/Valid; a reference from another amount, currency, Order or provider account is not sufficient. Persist authoritative evidence before a fallible Orders projection, so projection failure cannot erase external success.

The future charge boundary must distinguish Succeeded (verified matching charge/reference), Declined (definitive provider rejection), Pending (known unresolved processing) and Unknown (no authoritative outcome). Map these to Orders confirmation/recovery deliberately; the current bool/FailureCode interface does not already expose this richer protocol. ReconciliationRequired is a local resolution/escalation state for unsupported lookup, conflicts or insufficient evidence, not invented proof that the provider declined. Timeout is not failure; HTTP disconnection does not undo a payment. Unknown/Pending do not authorize another charge/refund or release ownership/tickets. A webhook is untrusted input until Payments verifies authentication/signature, intended account, replay identity and attempt/payload correlation. Persist callback identity and observations before acknowledgement; duplicate delivery must not repeat provider execution or a business transition. No webhook endpoint exists in this PR.

For refunds, retain immutable observations before fenced resolution. A referenced Succeeded result can survive an expired claim or projection failure; stale workers cannot overwrite a newer owner. Conflicting success/decline evidence must retain both observations and require ReconciliationRequired, not last-writer-wins. Identical observation replay is harmless; contradictory content for one identity is not. No automatic callback replay after ambiguous database commit: inspect the stable identity through a fresh scope. Stable provider idempotency must cover the full recovery horizon; unsupported/expired guarantees require controlled reconciliation, even after NotFound. Transport cancellation tokens request bounded I/O, not rollback of external effects.

### Refund-to-Loyalty flow: target versus implemented

The intended future sequence is: (1) Orders admits the refund; (2) commits its sole durable owner; (3) Payments submits or resolves the monetary attempt outside DB locks; (4) retains authoritative outcome evidence; (5) Orders rechecks its owner/source under lifecycle locks and finalizes eligible Order/Tickets; (6) in that local transaction stages the confirmed business fact through the existing Bus Outbox; (7) Loyalty persistently deduplicates it; (8) applies only the agreed consequences. A confirmed outcome must remain recoverable even if step 5 fails. Approval deadlines restrict new admission, not later resolution of an already approved operation.

The current TicketPurchased envelope carries persisted Order/session/payment facts but no provider attempt ID or original charge currency; do not assume the richer future Payments data already exists on that wire contract. Any required extension must be separately versioned/reviewed with Loyalty. This is **not an active confirmed-refund integration**. Today's PaidOrderCancellation instead journals legacy money then performs spent-points/GOLD compensation by existing RPCs **before** finalization; only its notifications are post-commit. Do not reorder it in this documentation PR. No confirmed-refund RabbitMQ pattern, DTO, source record or passive consumer has been agreed/implemented here. Before activation, review one versioned contract with immutable event ID, original Order/purchase/session correlation, sole refund operation identity, full-refund money/currency source, truthful confirmation/occurrence-time semantics, conflict/replay rules, routing and timestamp/serialization compatibility. Persist immutable source + Outbox atomically with the eligible business transition; retain independent monetary evidence if that transaction fails. Do not emit success for Approved, Pending or Unknown. Out-of-order refund-before-purchase delivery must retain evidence without fabricating a purchase. Keep internal actor/reason audit private unless explicitly required by the public contract.

| Loyalty consequence | Existing / future boundary |
| --- | --- |
| Restore points spent at checkout | Existing debit-linked full RefundPointsAsync with original `refund-{orderId}` deterministic key. Restores an existing debit; not earned reward reversal. Do not duplicate this via a future event without an explicit source-linked deduplication/ownership decision. |
| Reverse rewards earned from refunded purchase | Future Points Accounting/reversal/debt work; not implemented by existing RefundPointsAsync and not authorized by this handoff. Requires an agreed confirmed source fact, entitlement/provenance and event-time policy. |
| GOLD compensation | Existing RollbackGoldUpgradeAsync(userId, orderId) releases that owned reservation; successful repeat is a no-op and must not clear a different period's owner. Not a cash refund or reward-point debit. |

Positive-cash Paid orders with NULL PaidCurrency remain ineligible for automatic cancellation until reconciliation supplies authenticated original-charge evidence linking the exact Order/charge/provider account, amount, currency and outcome. A new failed eligibility attempt creates no cancellation owner and leaves normal Paid/Valid ticket use available (#98 correction). Do not backfill UAH, mutate immutable journal/source history, delete existing uncertain owners, or interpret this correction as permission to refund. Recording a verified historical correction still needs a reviewed auditable workflow; no reconciliation API/backfill exists here. Zero-cash cancellation needs only its truthful Loyalty compensation and never invents a cash charge/refund or currency.
