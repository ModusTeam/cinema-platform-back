# Orders application boundary

`Cinema.Orders.Application` owns order creation and cancellation commands, order history queries, the order DTO and mapping, the current order domain-event handlers, and reservation, checkout orchestration, and GOLD upgrade pricing services. Moved types keep their existing CLR namespaces. The Host registers the assembly and all three services with `AddOrdersApplication()`.

`Cinema.Orders.Domain` owns `Order`, `OrderStatus`, and `OrderPaidEvent`, `OrderFailedDomainEvent`, and `OrderCancelledDomainEvent`. Their CLR namespaces and event payloads are unchanged. It depends on SharedKernel for domain primitives and Scheduling.Domain for `Session` and `Seat`. It has no dependency on Tickets.Domain or legacy Cinema.Domain. `Order.UserId` remains a `Guid`; the shared EF model retains its foreign key to `User` in Identity.Domain.

`Cinema.Tickets.Domain` owns `Ticket` and `TicketStatus`. Its one-way reference to Orders.Domain is required by `Ticket.OrderId: EntityId<Order>`; Orders.Domain does not reference Tickets.Domain. Both domains retain their existing CLR namespaces. `TicketDto` and its mapping remain in the legacy application because ticket detail uses them. Order history projects Order-owned fields and loads visible Tickets for the selected OrderIds in one batched query.

Reservation creates a validated order without tickets, then creates and tracks tickets explicitly in the same transaction and `SaveChangesAsync` call. The remaining order factory retains the session, seat, price, and total validation. The Order/Ticket foreign key and cascade delete remain mapped without domain navigations. Checkout and cancellation query Tickets by persisted OrderId. Order event handlers query Tickets by OrderId and include locally added Tickets during pre-save event dispatch.

Checkout and loyalty previews, shared application interfaces, and `CancelExpiredOrdersJob` remain transitional. The Orders application temporarily depends on `Cinema.Application` for those contracts and the shared context. Payment, loyalty, Booking locks, RabbitMQ messages, SignalR notifications, and Hangfire behavior are unchanged. Persisted assembly-qualified names for moved domain and application types may refer to their former assemblies. Check external Hangfire jobs, serialized type metadata, and consumers before deployment; CLR namespaces alone do not preserve assembly-qualified identity.

Cancellation loads the Order first, then queries tracked Tickets by persisted OrderId with Session included. The event handler performs its own filtered Ticket query during SaveChanges; it does not rely on relationship fixup. As before, the non-admin cutoff uses the first returned ticket without an explicit sort; separate queries can observe intervening database changes and may return multiple tickets in a different order. PostgreSQL characterization tests cover fixup, event side effects, persisted refunds, and query filtering when a disposable pgvector database is configured.

## Persistence and remaining boundaries

`Cinema.Orders.Infrastructure` owns `OrderConfiguration`. It references Orders.Domain and Identity.Domain for the mapped entities and Scheduling.Infrastructure to reuse the existing UTC converter. `Cinema.Infrastructure` still owns the shared `ApplicationDbContext` and migrations and explicitly loads Orders configurations. The relationship and column mapping are unchanged. Orders Application still uses legacy `IApplicationDbContext` and shared application contracts. Checkout previews, loyalty and payment integrations, `CancelExpiredOrdersJob`, Ticket DTOs, and ticket endpoints remain in their current layers. See [Tickets](../Tickets/README.md) for the ticket boundary and [Scheduling](../Scheduling/README.md) for its shared-context dependency.

### Phase 3 persistence decision

Keep `IApplicationDbContext` shared for now. Reservation uses Seats, Sessions, Pricing, Orders, and Tickets in one EF transaction; checkout and order event handlers also query Tickets through the same context, and pre-save handlers inspect its `ChangeTracker`. Booking validators and Scheduling queries use the same shared model. Smaller module interfaces would leave these cross-module operations dependent on several contracts and still require the same context instance. The Host registers one scoped `ApplicationDbContext` as `IApplicationDbContext`; `Cinema.Infrastructure` remains the only context and migration owner.

Keep the current Orders.Infrastructure reference to Scheduling.Infrastructure for `DateTimeUtcConverter`. The converter is used by Scheduling, Orders, and legacy EF mappings. Moving it into Domain or SharedKernel would introduce EF Core there; creating another assembly or duplicating the converter would add complexity and risk divergent UTC behavior. This is an acknowledged Infrastructure dependency until a broader persistence ownership change justifies a different home.

`IApplicationDbContext.BeginTransactionAsync` passes its requested isolation level to EF Core. Reservation requests `ReadCommitted`; Catalog import calls `Database.BeginTransactionAsync(IsolationLevel.ReadCommitted, ct)` directly after casting the interface to `DbContext`. The shared SaveChanges interceptor still clears domain events and publishes them before persistence, including RabbitMQ and Redis side effects; a later database failure can leave those side effects visible, while a failed publish leaves the events cleared on that context. The interceptor now passes the SaveChanges cancellation token to its publishers. Durable publication remains a separate lifecycle decision.

EF still warns that required `Order → Session` and legacy `SeatLock → Seat` relationships point to entities with global query filters. A PostgreSQL regression confirms that including a filtered Session omits its Order; historical owner/admin reads deliberately bypass those filters. The legacy SeatLock entity is not used by the active Redis lock workflow. No mapping change is warranted for the current application queries.
