# Orders application boundary

`Cinema.Orders.Application` owns order creation and cancellation commands, order history queries, the order DTO and mapping, the current order domain-event handlers, and reservation, checkout orchestration, and GOLD upgrade pricing services. Moved types keep their existing CLR namespaces. The Host registers the assembly and all three services with `AddOrdersApplication()`.

This is an application-only extraction. `Order`, `Ticket`, their statuses and domain events, EF configurations, the shared `ApplicationDbContext`, and migrations remain in the legacy layers. `TicketDto` and its mapping remain in the legacy application because ticket detail uses them. Order history projects Order-owned fields and then loads visible Tickets for the selected OrderIds in one batched query; the application composes the existing DTOs from ticket queries by `OrderId`.

Reservation creates a validated order without tickets, then creates and tracks tickets explicitly in the same transaction and `SaveChangesAsync` call. The remaining order factory retains the session, seat, price, and total validation. The Order/Ticket foreign key and cascade delete remain mapped without domain navigations. Checkout and cancellation query Tickets by persisted OrderId. Order event handlers query Tickets by OrderId and include locally added Tickets during pre-save event dispatch.

Checkout and loyalty previews, shared application interfaces, and `CancelExpiredOrdersJob` remain transitional. The Orders application temporarily depends on `Cinema.Application` for those contracts and the shared context. Payment, loyalty, Booking locks, RabbitMQ messages, SignalR notifications, and Hangfire behavior are unchanged. Persisted assembly-qualified names for the moved service types should be checked before deployment if any external jobs serialize them.

Cancellation loads the Order first, then queries tracked Tickets by persisted OrderId with Session included. The event handler performs its own filtered Ticket query during SaveChanges; it does not rely on relationship fixup. As before, the non-admin cutoff uses the first returned ticket without an explicit sort; separate queries can observe intervening database changes and may return multiple tickets in a different order. PostgreSQL characterization tests cover fixup, event side effects, persisted refunds, and query filtering when a disposable pgvector database is configured.
